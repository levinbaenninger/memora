# Two-Factor Authentication: TOTP + encrypted backup codes via Better Auth twoFactor plugin

Memora adds a second authentication factor. The implementation uses Better Auth's `twoFactor` plugin in TOTP-only mode with backup codes for recovery. The plugin is configured with `allowPasswordless: true` so users whose only account is a Google OAuth account can also enroll. Enrollment scope and disable scope differ by account class:

- **Credential accounts (email + password)**: 2FA is *mandatory*. After sign-up + email verification, the `_app` route guard redirects users without `twoFactorEnabled` to a dedicated onboarding route at `/auth/setup-2fa`, which they cannot escape (other than signing out) until they complete enrollment. The settings page does not expose a Disable button, and the server `before` hook blocks `POST /two-factor/disable` for any user with a credential account by throwing `FORBIDDEN { code: TWO_FACTOR_REQUIRED }`. This means a credential user cannot turn 2FA off once it is on, even by hitting the API directly.
- **OAuth-only accounts (Google today)**: 2FA is *optional*. These users are not forced through the onboarding route and can enable or disable 2FA at will from settings (password prompt is skipped because of `allowPasswordless`). Google's own 2FA already serves as their second factor; Memora's 2FA on top is a self-service hardening option, not a policy.

Sign-in 2FA challenge by default only fires on Better Auth's credential sign-in endpoints (`/sign-in/email`, `/sign-in/username`, `/sign-in/phone-number`). For users who *opted in* to Memora's 2FA on an OAuth-only account, the plugin would otherwise not challenge them — the OAuth callback creates a session and treats the sign-in as complete. To keep their opt-in meaningful, an `after` middleware on `/callback/:id` and `/oauth-proxy-callback` checks `ctx.context.newSession.user.twoFactorEnabled`; if set, it mirrors the plugin's `/sign-in/email` after-hook (deletes the new session and its cookie, creates a `two_factor` signed verification cookie keyed off the user id, throws `ctx.redirect("/auth/two-factor")`). This is a guard, not an enforcement: it only triggers for users who already enabled 2FA themselves. The TOTP plugin's `verifyTwoFactor` helper reads the `two_factor` cookie when there is no session, so the existing `/auth/two-factor` challenge UI works unchanged.

Verification flow on sign-in lives at `/auth/two-factor` and is reached for credential sign-in via the client plugin's `onTwoFactorRedirect` callback, which dispatches a custom event that the root provider listens for and converts to `router.navigate({ to: "/auth/two-factor" })`. The `twoFactorPage` config is not used because it forces a full reload, conflicting with the SPA skeleton-first transition pattern in ADR-0005. The 2FA page accepts a TOTP code, offers an "I lost my authenticator — use a backup code" link to swap to the backup-code form, and exposes a "Trust this device for 30 days" checkbox unchecked by default. Onboarding (the credential-user wizard) lives at `/auth/setup-2fa` and runs a 3-step reui `Stepper` flow: confirm password → scan QR + show plain-text TOTP secret in a copyable `InputGroup` → display backup codes with Download / Copy-all and a mandatory "I have saved these codes" checkbox before the Continue button activates. Day-to-day management (regenerate backup codes; disable, for OAuth-only users) lives in the existing security tab at `/settings/security`. `@better-auth-ui/react@1.6.3` does not ship 2FA views, so all of the surfaces above are hand-built.

Backup codes use the plugin default `storeBackupCodes: "encrypted"`: symmetric encryption keyed off `BETTER_AUTH_SECRET`, so DB-only compromise does not leak codes. Hashing was considered but the plugin only accepts `"plain" | "encrypted" | { encrypt, decrypt }`, and a custom hash-only encryptor would block the `viewBackupCodes` fresh-session reveal flow without a material security gain on top of encryption. Backup-code generation defaults are kept (10 codes × 10 chars). The TOTP issuer is set to `"Memora"` via a new top-level `appName: "Memora"` in the Better Auth config (previously missing). `skipVerificationOnEnable` is left at default `false` so `twoFactorEnabled` flips only after the user successfully enters a TOTP code from their authenticator, preventing self-inflicted lockout if the QR step is abandoned mid-flow. The existing `/two-factor/*` rate-limit rule (5 reqs / 60s) already in `packages/auth/src/index.ts` is left in place.

## Considered options

- **Ship TOTP + email OTP together** — adds a softer recovery channel via the existing Resend pipeline. Rejected for v1: doubles UI surface (send/verify endpoints, resend cooldown, separate rate limits, error mapping), and backup codes already cover the lost-authenticator case. Email OTP is left as a follow-up; the chosen plugin shape does not block adding it later by passing `otpOptions.sendOTP`.
- **SMS OTP** — rejected: cost, deliverability, and SS7 attack surface make SMS the weakest mainstream 2nd factor; not appropriate for a service whose threat model justifies adding 2FA in the first place.
- **Require password to enroll (drop `allowPasswordless`)** — simpler default, matches the Better Auth doc's warning callout. Rejected: Memora has a real OAuth-only user path via Google, and forcing those users to set a password before enrolling would push them onto a credential surface they explicitly avoided. The security-improvements branch should give every account class access to 2FA, even if only credential users are *required* to use it.
- **Mandatory 2FA for OAuth-only users too** — uniform policy across account classes. Rejected: Google's own 2FA is already in place for the OAuth path, and forcing Memora-level TOTP on top of an IdP that the user has presumably already secured produces friction without a clear threat-model gain. Mandatory 2FA is reserved for the path where Memora itself owns the credential (email + password).
- **Skip the OAuth-callback after-hook entirely and "trust Google's own 2FA"** — was the original ADR-0009 position. Reconsidered: if an OAuth-only user explicitly opts in to Memora's 2FA from settings, signing in via Google without ever being challenged makes the opt-in meaningless. The custom after-hook on `/callback/:id` (and `/oauth-proxy-callback`) is therefore added as an *opt-in guard*, not as enforcement. Users who never enable 2FA see no behavior change on the OAuth path.
- **Allow credential users to disable 2FA from settings** — most apps do. Rejected: enforcement is the whole point. The Disable button is removed from the UI and the server `before` hook short-circuits `POST /two-factor/disable` with `FORBIDDEN { code: TWO_FACTOR_REQUIRED }` whenever the caller has a credential account, so direct API calls can't bypass it either.
- **Redirect non-enrolled credential users to `/settings/security` instead of a dedicated onboarding route** — was the first cut. Rejected after testing: the settings layout sits inside the app shell (sidebar, command menu) and looks like the user already has access. A dedicated `/auth/setup-2fa` route outside `_app` makes the gate obvious, hides the sidebar, and uses a reui `Stepper` to set expectations that this is a multi-step setup, not a tucked-away toggle.
- **`skipVerificationOnEnable: true`** — fewer clicks during enrollment. Rejected: the failure mode (user closes tab after seeing the QR, never confirms, locked out on next sign-in) is exactly the lockout 2FA is supposed to prevent. Backup codes mitigate but do not remove the bad UX.
- **Plain-text backup codes** — plugin default before 1.6 and still the documented default in some places. Rejected: the security-improvements branch's whole premise is that DB-only compromise should not unlock accounts. Encrypted is a one-line config change.
- **Custom hash-only backup-code encryptor (`{ encrypt: hash, decrypt: throw }`)** — strongest at rest. Rejected: breaks `viewBackupCodes` (the fresh-session reveal API). Marginal benefit over symmetric encryption keyed by `BETTER_AUTH_SECRET`, since an attacker who has the DB *and* the secret already owns the auth stack.
- **`twoFactorPage: "/auth/two-factor"` instead of `onTwoFactorRedirect`** — built-in, less code. Rejected: full page reload contradicts ADR-0005's skeleton-first SPA transitions. The callback variant uses TanStack Router navigation and preserves the in-flight auth client state.
- **Extend the `/auth/$path` catch-all with a "two-factor" view in `Auth.tsx`** — keeps one auth route. Rejected: `@better-auth-ui` does not include 2FA viewPaths in 1.6.3, so this is custom code regardless. A dedicated TanStack route makes the surface obvious and avoids coupling Memora-specific 2FA UI to a library catch-all that doesn't natively support it.
- **Run `npx @better-auth/cli generate` to author the drizzle schema** — automated, follows the doc's happy path. Rejected: Memora hand-authors `packages/db/src/schema/auth.ts` with explicit indices and relations; the CLI overwrites or duplicates these. Hand-author + `bun db:generate` matches the existing pattern in `0001`–`0008`.
- **`trustDevice: true` checked by default on the 2FA verify form** — friendliest UX. Rejected: defies the "security improvements" intent. The opt-in default still refreshes the cookie on each in-window sign-in, so a user who opts in once is not re-prompted unnecessarily.

## Consequences

- **Plugin wiring** (`packages/auth/src/index.ts`): adds `appName: "Memora"` at the top level and registers `twoFactor({ issuer: "Memora", allowPasswordless: true, backupCodeOptions: { storeBackupCodes: "encrypted" } })` in the `plugins` array. Default TOTP period (30s) and digits (6) are kept. The existing `/two-factor/*` custom rate-limit rule remains.
- **Enforcement hooks** (`packages/auth/src/index.ts`):
  - `before` middleware on `/two-factor/disable`: looks up the caller's accounts via `internalAdapter.findAccounts(userId)`; throws `APIError("FORBIDDEN", { code: "TWO_FACTOR_REQUIRED" })` if any account has `providerId === "credential"`. OAuth-only users fall through.
  - `after` middleware on `/callback/:id` and `/oauth-proxy-callback`: replicates the plugin's `/sign-in/email` after-hook for the OAuth path. If `ctx.context.newSession.user.twoFactorEnabled === true`, deletes the just-created session, clears the session cookie, creates a 10-minute verification record, sets the `two_factor` signed cookie, and throws `ctx.redirect("/auth/two-factor")`. The `two_factor` cookie name and shape match Better Auth's internal constant so the plugin's existing `verifyTwoFactor` helper picks it up unchanged.
- **Client wiring** (`apps/web/src/modules/auth/client.ts`): adds `twoFactorClient({ onTwoFactorRedirect })`. The callback dispatches a `memora:two-factor-redirect` custom event; `Providers` listens and calls `navigate({ to: "/auth/two-factor" })`. The custom-sign-in UI in `packages/ui/src/components/auth/sign-in.tsx` was patched so the `onSuccess` callbacks for `signInEmail` / `signInUsername` skip their `navigate(redirectTo)` when the response payload contains `twoFactorRedirect: true`, otherwise the redirect would race the 2FA navigation and the user would bounce off `/auth/sign-in`.
- **`_app` route guard** (`apps/web/src/routes/_app/route.tsx`): on every navigation under the authenticated shell, after the session check, reads `session.user.twoFactorEnabled`; if false and the user has a credential account (checked via a cached `listAccounts` query), redirects to `/auth/setup-2fa`. After enroll, the relevant cached queries (`["auth", "session"]`, `["auth", "accounts"]`) are explicitly `refetchQueries`-d, not just invalidated, because `ensureQueryData` returns cached data on stale and would otherwise loop the user back to setup.
- **DB schema** (`packages/db/src/schema/auth.ts`): adds nullable `twoFactorEnabled boolean` to `user`, plus a new `twoFactor` table with `id text pk`, `userId text fk(user.id) on delete cascade`, `secret text not null`, `backupCodes text not null`, `verified boolean default false not null`. Index on `user_id`. `bun db:generate` produces `packages/db/migrations/0008_young_warhawk.sql`.
- **Setup route** (`apps/web/src/routes/auth/setup-2fa.tsx`): outside `_app`. Own guard redirects no-session → sign-in, already-enrolled → dashboard. Renders `TwoFactorSetup` (a reui `Stepper`-driven wizard). The Continue button on the final step is disabled until the "I have saved these codes" checkbox is ticked. A "Sign out and finish later" link is always visible so users are never trapped.
- **Challenge route** (`apps/web/src/routes/auth/two-factor.tsx`): outside `$path` catch-all. Renders `TwoFactorChallenge` from `@memora/ui`: TOTP form by default, swap link to backup-code form, trust-device checkbox. Calls `authClient.twoFactor.verifyTotp` / `verifyBackupCode`. On success navigates to `/dashboard`. No SSR.
- **Settings 2FA card** (`apps/web/src/modules/app/ui/components/settings/security/two-factor.tsx`): mounted from `SecuritySettings` between `LinkedAccounts` and `ActiveSessions`. States: idle (Enable button when not enrolled; Regenerate-backup-codes button when enrolled — no Disable button), password prompt (for credential users on enable / regenerate), QR + verify (re-uses the same `SecretField` InputGroup pattern), one-time backup-code reveal with Download / Copy-all.
- **UI components** (`packages/ui/src/components/auth/two-factor/two-factor-challenge.tsx`, `packages/ui/src/components/reui/stepper.tsx`): the challenge form lives in `@memora/ui` because it has no app-side dependencies; the setup wizard lives in `apps/web/src/modules/auth/ui/two-factor-setup.tsx` because it needs the local `authClient` singleton.
- **New dependencies**: `qrcode.react` (pure-client SVG QR; no canvas) added to both `@memora/ui` and `apps/web`. reui `stepper` added to `@memora/ui` via `bunx shadcn add @reui/stepper`.
- **No new email**: enrollment confirmation emails are out of scope for v1. If audit emails are added later, hook them into the `after` middleware that already exists in `packages/auth/src/index.ts`.
- **OAuth challenge is opt-in by user, not by policy**: if an OAuth-only user never enrolls in 2FA, the OAuth callback path behaves identically to before this ADR. The after-hook is a no-op unless `newSession.user.twoFactorEnabled === true`. A future reader asking "why does my Google sign-in suddenly route through `/auth/two-factor`?" lands here: because that account opted in.
- **Tests**: integration coverage for (a) email-sign-in user with 2FA enabled is redirected after credential check, (b) TOTP verify with valid code succeeds and admits to `/dashboard`, (c) backup code is consumed and a second use of the same code fails, (d) attempt to call `POST /two-factor/disable` from a credential account returns `FORBIDDEN`, (e) OAuth-only account with 2FA enabled is redirected to `/auth/two-factor` after the Google callback, (f) credential user without 2FA is redirected to `/auth/setup-2fa` on every authenticated nav. Plugin internals (TOTP generation, secret encryption) are not re-tested.
- **No migration plan for existing users**: no production users yet. If a user base exists before this ships, add a settings-banner nudge rather than letting the `_app` guard kick everyone into onboarding on next sign-in.
