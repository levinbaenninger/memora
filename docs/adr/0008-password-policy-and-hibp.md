# Password Policy: complexity rules + HIBP breach check on all credential surfaces

Email/password authentication moves from Better Auth's default `minPasswordLength: 8` with no content rules to a stricter policy enforced on every surface that mints or rotates a password: sign-up, password reset, and the authenticated change-password flow in settings. A new password must be 12–128 characters and contain at least one uppercase letter, one lowercase letter, one digit, and one symbol (defined as `/[^A-Za-z0-9]/`, accepting Unicode punctuation so users are not punished for choosing § over `!`). It must also not appear in the Have I Been Pwned breach corpus, checked server-side via Better Auth's `haveIBeenPwned` plugin (k-anonymity SHA-1 prefix, no plaintext leaves the server). The plugin's default failure behavior is accepted as-is — HIBP availability is high enough and Memora is a personal-notes app, not a system where a brief HIBP outage blocking sign-up would matter.

The rule set lives in `packages/auth/src/password-policy.ts` as a pure function exported via the subpath `@memora/auth/password-policy`. The server `betterAuth` config imports it inside `emailAndPassword.password.validatePassword`; the client `<PasswordRequirements>` component in `packages/ui/src/components/auth/password-requirements.tsx` imports the same function to render a live on-focus checklist below the password field. The checklist uses gray-to-green transitions (no red flash on every keystroke) and the submit button is disabled until every client-checkable rule is green. HIBP is not checked live — only at submit — and surfaces as a Better Auth `password-compromised` error code mapped to a friendly toast: "This password appeared in a known data breach. Pick another." All copy is hardcoded English; Memora has no other i18n surface today.

## Considered options

- **Stay on Better Auth defaults (min 8, no content rules, no HIBP)** — zero work, less friction at sign-up. Rejected: 8-character passwords with no breach check are below the bar for any service holding user-authored content, and adding rules later forces password resets for the existing user base.
- **NIST SP 800-63B-aligned policy (length + HIBP only, no charset mixes)** — NIST explicitly discourages mandatory upper/lower/digit/symbol rules on the grounds that they push users toward predictable substitutions (`P@ssw0rd1!`) that reduce real entropy. Rejected by product choice: charset mixes were explicitly requested, the user base is small enough that the entropy concern is dominated by the HIBP check anyway, and "looks strong" UX signal has value beyond the math.
- **Block email-local-part substring inside the password** — common bad-practice guard ("john" inside `john1234`). Rejected: with min length 12 + HIBP + charset mixes, marginal additional protection is small, and it adds a rule that's annoying to explain in the checklist.
- **Grandfather existing users / force reset on next sign-in / soft-nudge banner** — migration strategies for pre-policy accounts. Rejected: no production users yet, so no migration logic is needed. Revisit if a real user base exists before the policy ships.
- **Client-only validation** — simpler, no server config change. Rejected: trivially bypassable; the policy has to be enforced where the password is hashed.
- **Server-only validation with no live checklist** — server is authoritative anyway. Rejected: users discover failures one rule at a time via submit-and-reject, which is the worst possible UX for an already-friction-heavy form. Live checklist removes the round-trip.
- **Per-route HIBP failure behavior (fail-closed on sign-up, fail-open on change-password to avoid mid-rotation lockout)** — defends against the unlikely case where HIBP outage blocks an authenticated user trying to rotate. Rejected: Better Auth's plugin is single-config and `pwnedpasswords.com` has high availability; the added complexity of a custom validator wrapper to branch by path is not justified at this app's scale.
- **Strength meter instead of per-rule checklist** — single bar, one summary label. Rejected: meters lie (`P@ssw0rd1!` reads "strong") and don't tell the user which rule is missing. Per-rule rows are more actionable.
- **Always-visible checklist vs. on-focus reveal** — always-visible is more discoverable. Rejected: clutters the form when the user is filling in name/email; on-focus reveal is hidden until relevant and stays open until all rules pass.
- **Extract a shared `<PasswordField>` component used by all three surfaces** — eliminates duplicated field code in sign-up, reset, and settings/change-password. Rejected for now: scope creep; the three sites can each render the existing local `PasswordField` plus a new `<PasswordRequirements>` underneath with a 3-line edit. Extract later if the pattern stabilizes.

## Consequences

- **New dependency**: Better Auth's `haveIBeenPwned` plugin is registered in `packages/auth/src/index.ts` with a custom error message: `"This password appeared in a known data breach. Pick another."`.
- **New module**: `packages/auth/src/password-policy.ts` exports a pure `validatePassword(pw: string): { valid: boolean; failed: PolicyRule[] }` plus the rule definitions (`MIN_LENGTH = 12`, `MAX_LENGTH = 128`, regex predicates). `packages/auth/package.json` gains a subpath export `./password-policy` so the file can be imported client-side without dragging in the `"use server"` Better Auth config.
- **Server wiring**: `emailAndPassword` config gains `minPasswordLength: 12`, `maxPasswordLength: 128`, and `password.validatePassword: (pw) => validatePassword(pw).valid` (or the equivalent shape Better Auth's current API expects). HIBP is enforced by the plugin in addition to the policy check.
- **New UI component**: `packages/ui/src/components/auth/password-requirements.tsx` exports `<PasswordRequirements password={pw} />`. Renders an on-focus list of rule rows (gray when unmet, green check when met). Imported by `sign-up.tsx`, `reset-password.tsx` (both in the same package), and `apps/web/.../settings/security/change-password.tsx`. No new package.
- **Submit gating**: each of the three forms disables its submit button until `validatePassword(pw).valid === true`. The button label and existing pending/spinner states are unchanged.
- **No localization extension**: copy lives in the new component, hardcoded English. Better Auth UI's `localization.auth.*` map is not extended for this work.
- **No migration**: with no production users, no banner, no forced reset, no sign-in-time policy check. If a user base exists before this ships, revisit with a soft-nudge banner in settings rather than a hard block at sign-in.
- **Tests**: unit tests cover `validatePassword` (each rule pass/fail in isolation, plus a few realistic combined inputs). HIBP is exercised through Better Auth's plugin and not re-tested here; integration coverage at the sign-up / reset / change-password level asserts that submitting a weak or breached password surfaces the correct error toast and does not create a session.
